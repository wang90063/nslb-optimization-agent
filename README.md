# NOA — NSLB Optimization Agent 🛰️

> 一个**自己迭代算法**的 agent。你给它一道网络负载均衡的优化题，它会自己写解法、自己跑评测、自己判断这版到底是好是坏、自己记笔记，然后接着写下一版——人只在「要不要把这版提交到线上」这一步介入。

*这是一个原型（prototype）。它针对的是一道具体的竞赛题（NSLB），但里面的三套机制——orchestrator 拆分、UCB 选方向、wiki 记忆——是可以搬到别的"反复试错、慢慢爬分"类任务上的。*

## 1. 这是什么 (What)

NOA 要解的题叫 **NSLB**（Network Switch Load Balancing，网络交换负载均衡），来自[华为云开发者大赛](https://developer.huaweicloud.com/competition/information/1300000256/introduction)：

> 在一个 leaf-spine 网络里，有一堆"流量"（flow）要从下层交换机（leaf）发到上层交换机（spine）。每条流要选一个上行端口（spine port）。选得不好，某些端口会被挤爆、某些闲着——负载不均衡。NOA 要做的，就是给每条流安排端口，让整网的负载尽量均匀。

这是一道**评分制**的优化题：解法的好坏由一个公式打分（越高越好），没有标准答案，只能一版一版往上爬。

**NOA 不是"帮你写一版解法"的工具，而是一个会自己长期迭代的 agent。** 它干的是这套循环：

```
写一版新解法  →  跑评测打分  →  和历史最好版对比，判断好坏
     ↑                                          │
     └────────  记笔记 + 挑下一个方向  ←─────────┘
```

人类只在一个地方介入：**决定要不要把某一版真的提交到线上评测机。** 因为线上分数是唯一本地算不出来的真值，而且提交对外可见、不可撤回——这步留给人。其余的写代码、跑分、判断、记录、挑方向，NOA 自己转。

## 2. 为什么要这么做 (Why)

让一个 LLM 反复迭代算法，会撞上三个很现实的坑。NOA 的三套核心机制，正好各治一个坑。

**坑一：context 会爆。** 一轮迭代要读 4000+ 行的 solver、读下界表、读评测器、跑很长的评测、写好几个文件。把这些全塞进一个对话里，几轮就把上下文撑满了——尤其想让它连续自转（`/loop`）的时候，越滚越大，很快触顶。
→ 用 **orchestrator + 用完即弃的 subagent**：主线只当协调者保留判断，把"读得多、回得少"和"按指令敲字"的脏活派给临时 subagent，它们各自在隔离的上下文里干完就丢。主线的 context 始终很轻。

**坑二：方向会选歪。** 试错空间很大，可走的方向几十个。纯随机试浪费时间，只挑"上次最有效"的又会一条道走到黑、错过没探过的富矿。
→ 用 **UCB 选方向**：把每类方向当成多臂老虎机的一只臂，按"已知收益 + 还没怎么试过的不确定性"打分排序，自动在"深挖已验证的"和"探索没试过的"之间平衡。

**坑三：判断会失忆。** 同一个死胡同，这次撞了、下次还撞。哪条路试过了、为什么死的、当时什么分——这些判断不沉淀下来，每轮都在重新踩坑。
→ 用 **wiki 记忆层**：把"事实"（分数、日志）和"判断"（这条路通不通、为什么）分开存，判断按**机制**而不是按文字检索，产新方向前先查"这路是不是已经死过了"。

这三套机制怎么落地，见 [第 5 节](#5-核心机制-how-it-works)。

## 3. 快速开始 (Getting Started)

环境：`g++`（支持 C++17）、`python3`。

```bash
# 1. 编译当前基线 solver
g++ -O2 -o versions/build/main versions/Solution.cpp

# 2. 在主排序数据集上打分
python3 scripts/score_manifest.py ./versions/build/main datasets/submit_core.txt

# 3. 看看现在该挑哪个方向（UCB 排序）
python3 .claude/skills/algorithm-iterate/scripts/ucb_frontier.py
```

让 NOA 自己跑一轮迭代，在 Claude Code 里调起主循环 skill：

```
/algorithm-iterate
```

想让它连续自转（自己一轮接一轮，直到撞到"该提交了"才停下来交还给你）：

```
/loop /algorithm-iterate
```

> ⚠️ **评测必须串行。** solver 内部用 `clock()` 做时间门控，多个评测并行抢 CPU 会让时间判断误触发，分数就不可复现了。NOA 的设计里，同一时刻只有一个评测在跑——别手动并行加速。

## 4. 一轮迭代长什么样 (The Loop)

NOA 每转一圈干这 8 件事。前几步是"想清楚要改什么"，中间是"改 + 验证"，最后是"记下来 + 决定下一步"。

1. **确认基线**：读当前最好版本的分、读结构性下界表（哪些指标还有空间、哪些已封死）。
2. **分析瓶颈**：派一个 recon subagent 去啃 solver/评测器，回报"瓶颈在哪、改哪几行，以及任何会推翻候选方向的约束事实"。
3. **挑方向 + 查重**：用 UCB 排序选这轮攻哪类方向；产新方向前先派 wiki subagent 查"这路是不是死过了"。
4. **写新版本**：新建 `Solution_YYYYMMDD_vN_描述.cpp`（绝不直接改基线），实现这一版的改动。
5. **评测**：派一个 eval subagent 在隔离上下文里编译 + 串行跑完所有分层数据集，只回结构化的分数摘要。
6. **判断取舍**：主线对照红绿灯规则判断——核心集真涨了吗？是不是只在"已知低转化"的家族上涨（红灯）？有没有触发硬否决项？
7. **记录**：分数和日志写进事实层（`SCORES.md` / `logs/`），这版的判断（通不通、为什么）派 wiki subagent 沉淀进记忆层。
8. **阶段自检**：读三个廉价信号，打印一行状态条——该继续迭代、该校准数据集、还是该换方向了。

> 🛑 **停止边界。** 当某一版达到"可以提交线上"的标准，NOA 会**停下来**，把版本和证据摆给你，等你决定要不要提交。它不会自己提交——线上是不可逆的对外动作，这步永远留给人。

> 🛰️ **卫星 skill。** 主循环之外还有三个被特定信号唤起的辅助 skill：`generate-dataset`（现有数据拉不开好坏算法的差距时，造更尖的新 case）、`calibrate-dataset`（攒满 3 次线上提交后，按线上相关性给数据集重新分层）、`wiki-maintain`（查重 + 沉淀判断）。它们的产出都回流到数据集，给主循环用。

## 5. 核心机制 (How It Works)

NOA 能长期自转，靠的是三套机制。下面每一套都先用大白话说"它解决什么坑、大致怎么干"，再用可展开的深挖块给出落地细节。

### 5.1 主线 orchestrator + 4 个 ephemeral subagent

**一句话：** 主线只当"包工头"，把累活外包给用完就丢的临时工，自己的脑子（context）始终很轻。

一轮迭代要读 4000+ 行的 solver、跑很长的评测、写一堆文件。如果全在一个对话里干，上下文几轮就满了。NOA 的办法是分工：

- **主线（orchestrator）**：保留**最终裁定权**——取舍走不走红绿灯、方向最后拍不拍板、这版结论是涨是退、wiki 状态怎么迁移。注意是"拍板"不是"全部判断"：方向的**初排建议、查重结论、风险预判**这些第一手判断是 subagent 给的，主线读它的回包后橡皮图章或推翻。留在主线的是那些**需要全局事实、且不可逆**的综合——一旦外包给隔离上下文，极容易和主线的事实漂移。
- **4 类临时工（ephemeral subagent）**：每个在自己干净的上下文里干一件"读得多/回得少"或"按指令敲字"的活，干完即弃，只把一小段结构化结果回报给主线。

| subagent | 干什么 | 读/写 | 回什么 |
|----------|--------|-------|--------|
| 🔍 analysis 分析 | 啃完 solver 定位瓶颈 + 查重 + 方向初排 | 只读 solver/下界/评测器/`wiki/` | 方向建议 + 改哪几行 + **约束事实** + 查重结论（试过没/死没死）+ 风险预判 |
| 🔧 impl 实现 | 按已批准方向新建版本文件、写改动、编译过 | 写 `versions/Solution_*.cpp` | 新文件名 + diff 摘要 + 编译结果 |
| ⚙️ eval 评测 | 串行独占跑五层 + candidate | 读 solver，跑评测 | 每层总分 + 逐 case 差值 + 每 case 运行时 |
| ✍️ wiki ingest 沉淀 | 按主线定的 spec 把判断写进记忆 | 写 `wiki/` | 改完确认，不自己下判断 |

**主线省下多少 context？** 大头是那份 **171KB ≈ 43k token 的 solver**：analysis 在隔离上下文里啃完它（外加下界表、评测器、整个 `wiki/`），只回一小段结构化建议；eval 的逐 case 长输出同样被挡在主线之外。这两笔每轮都发生、且在 `/loop` 连续自转里**不随轮数累积**——主线 context 始终很轻，这才是能长期自转的前提。（注：这是按文件体量做的结构估算；唯一实测到的 token 数字是 wiki 查重那条路，见 [5.3](#53-wiki-记忆层)。）

<details>
<summary><b>深挖：哪些判断外包、哪些不外包、recon 为什么必须问"约束事实"</b></summary>

**判断不是"全留主线"，而是分两层。** 第一手判断——方向初排、查重结论（这路试过没/死没死）、风险预判——交给 analysis subagent 在隔离上下文里做完，因为它要啃 4000+ 行 solver 和整个 wiki，读得多回得少。主线**绝不外包的是"拍板"那一层**：取舍红绿灯、方向最终采纳与否、verdict + 思路归属 + wiki 状态迁移、阶段自检。这些是把多个信号合成一个**不可逆结论**的 synthesis，而且依赖主线手里的全局事实——让隔离上下文的 subagent 来下，结论容易和主线漂移，甚至丢掉"推翻方向的关键事实"。一句话：**subagent 提议，主线裁定。**

最值钱的一条经验：**analysis 的 prompt 必须显式要求"返回任何与候选方向冲突或构成约束的事实"，不能只问"瓶颈在哪"。** 本项目几次关键判断都来自这种事实——比如一次读评测器发现某指标是"所有 job 的峰值之和"（sum-of-peaks），当场否掉了"记峰值替代求和"那个方向。如果只问瓶颈、不问约束，这类事实会被摘要丢掉，主线就会拿着错前提往下走。

**评测铁律（subagent 版）：**
1. 禁止多个 eval subagent 并行——solver 用 `clock()` 门控，并行抢 CPU 会让时间判断误触发，分不可复现。一轮只有一个 eval。
2. eval subagent 跑的时候，主线时段独占——这期间不派任何吃 CPU 的活（analysis/impl/ingest 都让路），否则等于变相并行。
3. "能进 subagent" ≠ "能并行"——把单个串行 eval 放进 subagent 只是为了把逐 case 的长输出移出主线 context，eval 本身仍是一个 solver 接一个跑。

</details>

### 5.2 UCB 选方向

**一句话：** 把"挑下一个改进方向"当成多臂老虎机问题，自动在"深挖已验证有效的路"和"探索没怎么试过的路"之间平衡。

可走的方向有几十个，分成若干"家族"（family）——比如改 SA 退火、改端口一致性、改全局定价等等。问题是该挑哪个？

- 只挑"上次涨分最多的"——会一条道走到黑，错过没探过的富矿。
- 纯随机挑——浪费时间在已知的死路上。

UCB（Upper Confidence Bound）给每个家族算一个分数，按这个分数排序选方向：

```
UCB(family) = V + C · √( ln N / n )
              └─┘   └──────────────┘
            已知收益      还没怎么试过的"不确定性奖励"
```

试得越少（`n` 越小）的家族，右边那项越大——哪怕它目前看着收益一般，也会被"不确定性"顶上去，逼着系统去探一探。完全没试过的家族（`n=0`）直接排最前。

<details>
<summary><b>深挖：收益 V 怎么算、成本为什么是闸门不是连续项、三层奖励回退</b></summary>

**收益 V 怎么算（prior 与实测的混合）：**

```
V = (1 − w) · prior_insight + w · observed
w = n / (n + k)   , k ≈ 3
```

一个家族刚开始试的时候（`n` 小），收益主要信"先验判断"（`prior_insight`，来自 wiki 里跨思路的硬结论）；试得多了（`n` 大），`w` 趋近 1，收益就主要信"实测涨跌"（`observed`）。`k≈3` 是这个过渡的快慢——大约试 3 次后，实测开始压过先验。

**成本是闸门，不是连续项。** 直觉上想把"改动成本"也塞进 UCB 公式当一个减项，但那样会让"便宜但没用"的方向虚高。NOA 的做法是把成本当**闸门**：超过预算的方向直接出局，没超的一视同仁——成本只决定"能不能进场"，不决定"排多前"。

**三层奖励回退（observed 从哪来）：** 实测收益按可信度分三层，能拿到高层就不用低层：
1. **线上 Δ**（最可信）——这版真提交了，有线上分差。
2. **本地 Δ × 转化率**——只有本地分差时，乘一个折扣。这个折扣是吃过亏定下来的：v318 本地涨 +0.20、线上只涨 +0.01，约 5% 转化率，所以本地涨分要大打折扣才能当真。
3. **status 映射**（兜底）——连本地分差都没有，就用 wiki 里这条思路的状态（主线/部分有效/封死）粗略映射一个值。

**prior_insight 的跨臂隔离：** 一个家族的先验判断只来自它自己的历史，不会被别的家族的成败串味——避免"隔壁那条路火了，连带高估这条"。

阶段自检每轮会打印一行状态条，报当前家族的 UCB 和全场最高的 UCB；当前家族不再是最高时，提示该换方向了。连续 5 轮无正增量是保底提醒——同一方向磨太久必须换结构性不同的路，禁止只调参数/顺序/gate 的"伪切换"。

</details>

### 5.3 wiki 记忆层

**一句话：** 把"事实"和"判断"分开存，让 NOA 记得哪条路试过、为什么死，下次产方向前先查，不再重复撞墙。

> 这套机制借鉴了 Karpathy 的 [LLM wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) 模式：让 LLM 增量维护一个持久、互相链接的 markdown wiki，作为"会复利增长的知识沉淀物"夹在你和原始资料之间——不像普通 RAG 每次都去重查原文，而是把知识编译一次、之后持续保鲜。NOA 把它落到算法迭代场景：原始资料是每版的分数与日志，wiki 沉淀的是"哪条思路通不通"的判断。

最大的浪费是失忆：同一个死胡同，这次撞了下次还撞。NOA 用一个 `wiki/` 目录当长期记忆，里面装的是上百版迭代攒下的**判断**，沉淀成两类可检索的页：

- **`ideas/`（当前 43 条思路页，一思路一页）**：每页记这条思路的**状态**（主线 / 部分有效 / 待试 / 封死）、关联的**版本外键**（`v236`、`v250`… 指回 SCORES 的事实行）、线上/本地分、**死因**，以及**思路之间的边**（A 启发了 B、C 取代 D、E 和 F 互斥）。
- **`insights/`（当前 18 条跨思路硬结论）**：不绑定单条思路、被反复验证过的规律——比如"本地涨分约 5% 转化到线上""SA 搜索空间已挖尽"。

外加 `index.md`（按状态/family 分组的目录）和 `log.md`（时间线 + sync 水位）。靠**两条分界线**保证它不烂：

- **事实 vs 判断分开。** 分数、日志、提交记录这些"客观发生过的事"写在 `SCORES.md` / `logs/`（事实层）；"这条路通不通、为什么、现在是主线还是封死"这些"判断"写在 `wiki/`（判断层）。两边不重复——事实变了不用动判断，判断变了不用动事实。
- **按机制检索，不按文字。** 查"这路试过没"，比的不是标题字面像不像，而是**底层机制**是不是同一回事。换个说法重新包装的老死路，照样能被认出来。

每轮迭代结束，新版本的判断会被沉淀回 wiki：这版属于哪条思路、verdict 是涨是退、状态怎么迁移（待试→封死 / 新增主线）。产新方向前，先查 wiki 确认不是在重走死路。

**和 UCB 的关系：wiki 不只是给人查的，它是 [UCB 选方向](#52-ucb-选方向)的结构化输入。** [`ucb_frontier.py`](.claude/skills/algorithm-iterate/scripts/ucb_frontier.py) 每轮直接解析 `wiki/ideas/*.md` 的 frontmatter，把判断喂进公式：

- **`status`** → UCB 收益的 status 兜底层（主线 +3 / 部分有效 +1 / 待试 0 / 封死 −1），也用来区分一个 family 是"还活着"还是"整条都封死了"。
- **`[[insight:...]]` 边** → UCB 的 `prior_insight`：撞到高入度的"封死墙"就压低先验，挂着"还有空间"类 insight 就抬高。那条 5% 转化率的教训（来自 [`local-online-divergence`](wiki/insights/local-online-divergence.md) insight）正是这么进到本地 Δ 折扣里的。
- **`versions` 外键** → UCB 的 `n`（family 试了几版）和 `N`（全场总版本数），决定探索项 `√(ln N / n)` 多大。

于是闭环成立：**wiki 沉淀判断 → UCB 读判断挑方向 → 跑出新版本 → 判断再沉淀回 wiki**。第 5.2 节那套"先验 vs 实测的混合"，先验那一半的数据源就是这里。

<details>
<summary><b>深挖：比 grep 省在哪（实测）、sync 水位对账、判断不外包</b></summary>

**为什么不直接 grep logs，要单独编译一层 wiki？** 我们在 skill workspace 做过一次消融：拿 3 个真实查重问题（"分两阶段先压 MM 再降 CB 试过没""给 SA 提案加 prefport 偏置呢""初始解能不能用 min-cost flow"），对比两条路——**查 wiki** vs **禁用 wiki、退回去翻原始 `SCORES.md` + `logs/`**。

两条路**答案完全一样**（3/3 命中、同样的证据版本、同样的死因）——所以差的不是对错，是**成本**：

| | 查 wiki | 退回翻 logs |
|---|---|---|
| 平均 token | **30.7k** | 41.8k |
| 要啃的原始文本 | index（97 行）+ 1-2 页 idea | `SCORES.md` 81 行 + `logs/` 4490 行（~271KB） |

平均省 **27% 的 token**（单题最高省 43%），要扫的原始文本差约 **45 倍**。

省在哪很关键：**省的不是 grep 那一下，是 grep 之后那一大片**。`logs/` 按"天"存事件流，而查重按"思路"问——两根轴是垂直的，一条思路（比如 `sa-proposal-bias`）跨好几天连载，grep 只能定位到一行，但状态/线上Δ/死因都写在命中行前后的叙事里，于是 grep 完必须 read 一片；措辞不撞词时（查的人说"压最大负载"、日志写"MM/sa_max"）grep 直接失灵，被迫整天通读；最后还要"确认没漏报"——否定命题没法用 grep 证明，只能过度读来防漏。**wiki 把这三笔开销一次性预编译掉了**：把存储轴从"按天"转成"按思路"，查询就从"横扫 N 天现场综合"塌缩成"index 定位→读 1-2 页"。历史越厚，杠杆越大——翻 logs 的成本随版本数线性涨，查 wiki 基本恒定。

**sync 水位对账：** 事实层（SCORES/logs）和判断层（wiki）是两套文件，靠 `log.md` 里的一个"水位线"对账——记录 wiki 已经消化到哪个版本了。新提交的版本如果还没沉淀进 wiki，水位线就落后，自检时能发现"有 N 个版本的判断还没记"，提醒补上。这样两层不会悄悄失同步。

**事实/判断的真相源边界：**

| 问题 | 去哪查 | 不去哪查 |
|------|--------|----------|
| 这版线上多少分 | `SCORES.md` / `online_ledger.md`（事实层） | 不去 wiki（判断层可能滞后） |
| 这条路为什么死的 | `wiki/ideas/<slug>.md`（判断层） | 不去 logs（事实层不存因果判断） |
| 现在主线是哪条 | `wiki/index.md` | — |

判断写进 wiki 的活由 wiki ingest subagent 按主线给的 spec 执行（见 [5.1](#51-主线-orchestrator--4-个-ephemeral-subagent)）——主线先定好 verdict、思路归属、状态迁移这三件"判断"，subagent 只负责按 spec 敲字，不自己下判断。

</details>

## 6. 成绩进展 (Score Progression)

从最初的 round-robin 基线一路爬到接近第一名。下面是有代表性的里程碑版本，标了每版属于哪个**家族**、主要在攻哪个**指标**（完整排行榜见 [SCORES.md](SCORES.md)）：

| 版本 | 线上分 | 家族 | 主要提升 | 关键改动 |
|------|--------|------|----------|----------|
| v1 | 276 | — | 基线 | round-robin |
| v8 | 347 | 初始解 | 整体结构 | per-flow 逐流独立选端口（+21） |
| v43 | 359 | portfolio | 候选多样性 | 3 策略 ensemble |
| v62 | 366.25 | 比较器 | MM / 瓶颈 | 词典序比较器 jm→fg→ci→future（优先压最大负载） |
| v138 | 369.12 | PC | CB（相位间 Cbtphsc） | score-aware 端口一致性 + 全局压力 tie-break |
| v232 | 369.65 | SA | CB（退火降冲突） | SA 退火预算收紧 |
| v292 | 369.73 | SA | CB（高冲突卡聚焦） | 三轮 focused SA + cross_dest 恢复 |
| v369 | 369.86 | cross_dest | CB（任务间 Cbttskc） | cross_dest top-3 混合打分 |
| v430 | 369.89 | pipeline | 运行预算（解锁大 case 后段） | time_tight 阈值放宽 4.5s→7.0s |
| **v454** | **370.15** | **global_state** | **MM（global_out 准确性）** | **actual global_out + CB-aware 贪心 portfolio** |

> **MM** = 最大负载瓶颈（评分公式里的 `40/Maxsingler + 40/Maxmultir` 项）；**CB** = 冲突罚分（`Cinphsc/Cbtphsc/Cbttskc` 三类，权重 12/5/3）。这两个是评分公式仅有的两大杠杆。

**看家族+指标能看出一条清晰的弧线：** 早期（v8–v62）靠结构性改动和压 MM 拿大头；一旦 MM 触到信息论下界、再压不动（见 wiki insight [`proxy-at-info-bound`](wiki/insights/proxy-at-info-bound.md)、[`mm-tight-bound-unreachable`](wiki/insights/mm-tight-bound-unreachable.md)），中后段（v138–v369）几乎全是在不同家族里换着法子降 **CB**——PC 降相位间冲突、SA 退火降冲突、cross_dest 降任务间冲突。最后 v454 又回到 MM，但走的是"把 global_out 的保守近似换成真值"这唯一一道还没堵死的缝，而不是硬压。

**当前最佳：370.15（v454），最终排名27（三等奖）。**（注：这个分数是w/o wiki和ucb的NOA版本获得的）

一个值得记的教训藏在 v318：本地涨了 +0.20、看着是绿灯，线上只涨 +0.01——约 5% 的转化率。这条经验后来被写进 UCB 的奖励折扣里（见 [5.2 深挖](#52-ucb-选方向)），从此本地分差要打折才能当真。
