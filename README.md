# NOA — NSLB Optimization Agent 🛰️

> 一个**自己迭代算法**的 agent。你给它一道网络负载均衡的优化题，它会自己写解法、自己跑评测、自己判断这版到底是好是坏、自己记笔记，然后接着写下一版——人只在「要不要把这版提交到线上」这一步介入。

*这是一个原型（prototype）。它针对的是一道具体的竞赛题（NSLB），但里面的四套机制——orchestrator 拆分、idea graph 选方向、wiki 记忆、分层数据集——是可以搬到别的"反复试错、慢慢爬分"类任务上的。*

> 📦 **选方向机制在演进中，按版本号迭代。** 当前是 **v0.0.2**（idea graph 富图 + LLM 探索/利用原则）；上一代 **v0.0.1** 是 UCB 标量选方向，因样本饥死退役。换代原因见[版本演进](#8-版本演进-changelog)。

## 1. 这是什么 (What)

NOA 要解的题叫 **NSLB**（Network Switch Load Balancing，网络交换负载均衡），来自[华为云开发者大赛](https://developer.huaweicloud.com/competition/information/1300000256/introduction)：

> 在一个 leaf-spine 网络里，有一堆"流量"（flow）要从下层交换机（leaf）发到上层交换机（spine）。每条流要选一个上行端口（spine port）。选得不好，某些端口会被挤爆、某些闲着——负载不均衡。NOA 要做的，就是给每条流安排端口，让整网的负载尽量均匀。

这是一道**评分制**的优化题：解法的好坏由一个公式打分（越高越好），没有标准答案，只能一版一版往上爬。

**NOA 不是"帮你写一版解法"的工具，而是一个会自己长期迭代的 agent。** 它干的是这套循环：

```
写一版新解法  →  跑评测打分  →  和历史最好版对比，判断好坏
     ↑                                          │
     └────────  记笔记 + 挑下一个方向  ←─────────┘
```

人类只在一个地方介入：**决定要不要把某一版真的提交到线上评测机。** 因为线上分数是唯一本地算不出来的真值，而且提交对外可见、不可撤回——这步留给人。其余的写代码、跑分、判断、记录、挑方向，NOA 自己转。

## 2. 为什么要这么做 (Why)

让一个 LLM 反复迭代算法，会撞上四个很现实的坑。NOA 的四套核心机制，正好各治一个坑。

**坑一：context 会爆。** 一轮迭代要读 4000+ 行的 solver、读下界表、读评测器、跑很长的评测、写好几个文件。把这些全塞进一个对话里，几轮就把上下文撑满了——尤其想让它连续自转（`/goal`）的时候，越滚越大，很快触顶。
→ 用 **orchestrator + 用完即弃的 subagent**：主线只当协调者保留判断，把"读得多、回得少"和"按指令敲字"的脏活派给临时 subagent，它们各自在隔离的上下文里干完就丢。主线的 context 始终很轻。

**坑二：方向会选歪。** 试错空间很大，可走的方向几十个。纯随机试浪费时间，只挑"上次最有效"的又会一条道走到黑、错过没探过的富矿。
→ 用 **idea graph 选方向**：一个确定性脚本把每类方向的记账事实（试了几版、撞了哪些死墙、有没有待试 idea）和思路间的演化拓扑铺成一张富图，再由 LLM 按探索/利用原则读图拍板——在"深挖已验证的"和"探索没试过的"之间平衡，并用"死墙传染"剪掉那些命运已被相邻死路预言的伪新方向。（早期 v0.0.1 用 UCB 标量自动排序，因样本饥死退役，见[版本演进](#8-版本演进-changelog)。）

**坑三：判断会失忆。** 同一个死胡同，这次撞了、下次还撞。哪条路试过了、为什么死的、当时什么分——这些判断不沉淀下来，每轮都在重新踩坑。
→ 用 **wiki 记忆层**：把"事实"（分数、日志）和"判断"（这条路通不通、为什么）分开存，判断按**机制**而不是按文字检索，产新方向前先查"这路是不是已经死过了"。

**坑四：本地分会骗你。** 真值（线上分）不可逆、要人肉、还稀缺——不可能每版都去问。于是只能靠本地评测代打分。但本地涨 ≠ 线上涨：v318 本地涨 +0.20、线上只涨 +0.01（5% 转化率）。如果本地集选得不对，agent 会一路朝着"本地好看、线上没用"的方向自欺。
→ 用 **分层数据集**：把本地集按"线上相关性"分成好几层各司其职（主排序 / 反向诊断 / 硬否决 / 观察验证…），再用两个卫星 skill 让这套分层自己进化——`generate-dataset` 在现有 case 拉不开好坏算法时造更尖的新 case，`calibrate-dataset` 攒够线上反馈后按真实相关性给 case 重新分层。本地分因此越用越像线上分。

这四套机制怎么落地，见 [第 5 节](#5-核心机制-how-it-works)。

## 3. 快速开始 (Getting Started)

环境：`g++`（支持 C++17）、`python3`。

```bash
# 1. 编译当前基线 solver
g++ -O2 -o versions/build/main versions/Solution.cpp

# 2. 在主排序数据集上打分
python3 scripts/score_manifest.py ./versions/build/main datasets/submit_core.txt

# 3. 看看现在该挑哪个方向（生成 idea graph 富图，LLM 读图拍板）
python3 .claude/skills/algorithm-iterate/scripts/idea_graph.py
```

让 NOA 自己跑一轮迭代，在 Claude Code 里调起主循环 skill：

```
/algorithm-iterate
```

想让它连续自转（自己一轮接一轮，直到撞到"该提交了"才停下来交还给你）：

```
/goal 迭代到出现一个按 acceptance.md 红绿灯达标的可提交版本
```

`/goal` 是 Claude Code 内置命令：你给它一个可验证的完成条件，评估器每轮核验，命中"可提交版本"就停下来把版本和证据摆给你——线上提交永远留给人（见 [第 4 节停止边界](#4-一轮迭代长什么样-the-loop)）。

> ⚠️ **评测必须串行。** solver 内部用 `clock()` 做时间门控，多个评测并行抢 CPU 会让时间判断误触发，分数就不可复现了。NOA 的设计里，同一时刻只有一个评测在跑——别手动并行加速。

## 4. 一轮迭代长什么样 (The Loop)

NOA 每转一圈干这 8 件事。前几步是"想清楚要改什么"，中间是"改 + 验证"，最后是"记下来 + 决定下一步"。

1. **确认基线**：读当前最好版本的分、读结构性下界表（哪些指标还有空间、哪些已封死）。
2. **分析瓶颈**：派一个 recon subagent 去啃 solver/评测器，回报"瓶颈在哪、改哪几行，以及任何会推翻候选方向的约束事实"。
3. **挑方向 + 查重**：跑 `idea_graph.py` 生成富图，LLM 按探索/利用原则读图选这轮攻哪类方向；产新方向前先派 wiki subagent 查"这路是不是死过了"。
4. **写新版本**：新建 `Solution_YYYYMMDD_vN_描述.cpp`（绝不直接改基线），实现这一版的改动。
5. **评测**：派一个 eval subagent 在隔离上下文里编译 + 串行跑完所有分层数据集，只回结构化的分数摘要。
6. **判断取舍**：主线对照红绿灯规则判断——核心集真涨了吗？是不是只在"已知低转化"的家族上涨（红灯）？有没有触发硬否决项？
7. **记录**：分数和日志写进事实层（`SCORES.md` / `logs/`），这版的判断（通不通、为什么）派 wiki subagent 沉淀进记忆层。
8. **阶段自检**：读三个廉价信号，打印一行状态条——该继续迭代、该校准数据集、还是该换方向了。

> 🛑 **停止边界。** 当某一版达到"可以提交线上"的标准，NOA 会**停下来**，把版本和证据摆给你，等你决定要不要提交。它不会自己提交——线上是不可逆的对外动作，这步永远留给人。

> 🛰️ **卫星 skill。** 主循环之外还有三个被特定信号唤起的辅助 skill：`generate-dataset`（现有数据拉不开好坏算法的差距时，造更尖的新 case）、`calibrate-dataset`（攒满 3 次线上提交后，按线上相关性给数据集重新分层）、`wiki-maintain`（查重 + 沉淀判断）。它们的产出都回流到数据集，给主循环用。

## 5. 核心机制 (How It Works)

NOA 能长期自转，靠的是四套机制。下面每一套都先用大白话说"它解决什么坑、大致怎么干"，再用可展开的深挖块给出落地细节。

### 5.1 主线 orchestrator + 4 个 ephemeral subagent

**一句话：** 主线只当"包工头"，把累活外包给用完就丢的临时工，自己的脑子（context）始终很轻。

一轮迭代要读 4000+ 行的 solver、跑很长的评测、写一堆文件。如果全在一个对话里干，上下文几轮就满了。NOA 的办法是分工：

- **主线（orchestrator）**：保留**最终裁定权**——取舍走不走红绿灯、方向最后拍不拍板、这版结论是涨是退、wiki 状态怎么迁移。注意是"拍板"不是"全部判断"：方向的**初排建议、查重结论、风险预判**这些第一手判断是 subagent 给的，主线读它的回包后橡皮图章或推翻。留在主线的是那些**需要全局事实、且不可逆**的综合——一旦外包给隔离上下文，极容易和主线的事实漂移。
- **4 类临时工（ephemeral subagent）**：每个在自己干净的上下文里干一件"读得多/回得少"或"按指令敲字"的活，干完即弃，只把一小段结构化结果回报给主线。

| subagent | 干什么 | 读/写 | 回什么 |
|----------|--------|-------|--------|
| 🔍 analysis 分析 | 啃完 solver 定位瓶颈 + 查重 + 方向初排 | 只读 solver/下界/评测器/`wiki/` | 方向建议 + 改哪几行 + **约束事实** + 查重结论（试过没/死没死）+ 风险预判 |
| 🔧 impl 实现 | 按已批准方向新建版本文件、写改动、编译过 | 写 `versions/Solution_*.cpp` | 新文件名 + diff 摘要 + 编译结果 |
| ⚙️ eval 评测 | 串行独占跑五层 + candidate | 读 solver，跑评测 | 每层总分 + 逐 case 差值 + 每 case 运行时 |
| ✍️ wiki ingest 沉淀 | 按主线定的 spec 把判断写进记忆 | 写 `wiki/` | 改完确认，不自己下判断 |

**主线省下多少 context？** 大头是那份 **171KB ≈ 43k token 的 solver**：analysis 在隔离上下文里啃完它（外加下界表、评测器、整个 `wiki/`），只回一小段结构化建议；eval 的逐 case 长输出同样被挡在主线之外。这两笔每轮都发生、且在 `/goal` 连续自转里**不随轮数累积**——主线 context 始终很轻，这才是能长期自转的前提。（注：这是按文件体量做的结构估算；唯一实测到的 token 数字是 wiki 查重那条路，见 [5.3](#53-wiki-记忆层)。）

<details>
<summary><b>深挖：哪些判断外包、哪些不外包、recon 为什么必须问"约束事实"</b></summary>

**判断不是"全留主线"，而是分两层。** 第一手判断——方向初排、查重结论（这路试过没/死没死）、风险预判——交给 analysis subagent 在隔离上下文里做完，因为它要啃 4000+ 行 solver 和整个 wiki，读得多回得少。主线**绝不外包的是"拍板"那一层**：取舍红绿灯、方向最终采纳与否、verdict + 思路归属 + wiki 状态迁移、阶段自检。这些是把多个信号合成一个**不可逆结论**的 synthesis，而且依赖主线手里的全局事实——让隔离上下文的 subagent 来下，结论容易和主线漂移，甚至丢掉"推翻方向的关键事实"。一句话：**subagent 提议，主线裁定。**

最值钱的一条经验：**analysis 的 prompt 必须显式要求"返回任何与候选方向冲突或构成约束的事实"，不能只问"瓶颈在哪"。** 本项目几次关键判断都来自这种事实——比如一次读评测器发现某指标是"所有 job 的峰值之和"（sum-of-peaks），当场否掉了"记峰值替代求和"那个方向。如果只问瓶颈、不问约束，这类事实会被摘要丢掉，主线就会拿着错前提往下走。

**评测铁律（subagent 版）：**
1. 禁止多个 eval subagent 并行——solver 用 `clock()` 门控，并行抢 CPU 会让时间判断误触发，分不可复现。一轮只有一个 eval。
2. eval subagent 跑的时候，主线时段独占——这期间不派任何吃 CPU 的活（analysis/impl/ingest 都让路），否则等于变相并行。
3. "能进 subagent" ≠ "能并行"——把单个串行 eval 放进 subagent 只是为了把逐 case 的长输出移出主线 context，eval 本身仍是一个 solver 接一个跑。

</details>

### 5.2 idea graph 选方向

> 🧭 这是 NOA 选方向机制的 **v0.0.2**。上一代 v0.0.1 用 UCB 标量自动排序，因样本饥死退役——换代的完整原因见[第 8 节版本演进](#8-版本演进-changelog)。

**一句话：** 把"挑下一个改进方向"拆成两半——客观记账交确定性脚本铺成一张富图，价值判断交 LLM 读图拍板，在"深挖已验证的路"和"探索没试过的路"之间平衡。

可走的方向有几十个，分成若干"家族"（family）——比如改 SA 退火、改端口一致性、改全局定价等等。问题是该挑哪个？

- 只挑"上次涨分最多的"——会一条道走到黑，错过没探过的富矿。
- 纯随机挑——浪费时间在已知的死路上。

NOA 的做法是**记账归脚本、判断归 LLM**。一个"选方向"决策捆了两个能力要求相反的子任务：

- **探索记账**（各家族试了几版 `n`、撞了哪些死墙、有没有待试 idea、思路间的演化拓扑）——客观、繁琐、LLM 容易数错 → 交确定性脚本 [`idea_graph.py`](.claude/skills/algorithm-iterate/scripts/idea_graph.py)，它产一张**富图**（记账事实 + DAG 拓扑），不算任何裁决分。
- **价值判断**（这条 +0.5 是不是早期弱基线虚高的？某条"待试"是真没试过、还是已被相邻死路预言？该深挖还是该跳？）——需要看穿均值、顺结构推理 → 交 LLM。

LLM 读富图时按四条探索/利用原则拍板：

1. **exploit**——家族有"主线/部分有效"的活 idea 且没挖透（`n` 还小）→ 收益真、该深挖。别被均值骗：整体均值低的家族里，只要**单条**活 idea 的原始回报亮眼，就顺它的变体边继续挖。
2. **explore**——跳去 `n` 小、又没被死墙预言的方向；完全没试过的家族（`n=0`）优先。
3. **剪枝（死墙传染）**——一条"待试"若自己撞了高入度死墙、或顺边邻接一个撞死墙的封死节点，它的"没试过"是假的、命运已被相邻方向预言 → 剪掉，不当新方向去试。这是替代 UCB 先验的因果信号。
4. **cost 门控**——有便宜活路时别先碰贵的（换框架 / 上 LP solver 这类 expensive 档，仅当所有便宜档都试穿才考虑）。

**一个具体例子：为什么"两条都没试过的路"该挑哪条。** 假设这轮 `idea_graph.py` 吐出这样一张图，桌上摆着两个候选方向，乍看都是"待试、没写过代码"：

```
方向 A：min-cost-flow 初始解   ── 待试 ──→ 撞墙 [portfolio-diversity-matters]（入度 6 ⚠️）
方向 B：cross_dest pair 分支     ── 待试 ──→ 不撞任何高入度死墙
```

`idea_graph.py` 数出一条关键事实：**方向 A 撞的那堵墙 `portfolio-diversity-matters` 入度 6**——已经有 6 条来自不同家族的思路都撞死在这堵墙上了。LLM 读到这条边，顺结构推断：方向 A 的"没试过"是假的，它的命运已被 6 个邻居预言，写出来大概率同样的死法（原则③剪枝）；方向 B 不沾任何高入度死墙，才是真·开阔（原则②）→ **这轮选 B**。

这里要说句公道话：**上一代 UCB 其实也能分出 A 和 B。** `ucb_frontier.py`（已随 v0.0.2 删除，见[第 8 节](#8-版本演进-changelog)）给撞高入度封死墙的 family 在先验里减一个常数（`prior -= 1.0`），`n=0` 时这个先验就是它的全部得分，于是 A 排在 B 后面——结论一样。差别在**怎么用这堵墙**：

| | UCB（v0.0.1） | idea graph（v0.0.2） |
|---|---|---|
| 墙的入度 6 | 压成一个 `−1.0` 的常数减项 | 原样摆在图上 |
| 阈值"入度≥5 才算高墙" | 硬编码 `HIGH_WALL_DEGREE=5`，拍的 | LLM 看具体入度和那 6 条思路死得有多干净，自己判断 |
| 墙上还有活 idea 时 | 要在代码里特判"此路难走但走得通" | 图上直接看到墙上挂着主线节点，顺手判断 |

换句话说，换代不是因为 UCB"看不见墙"，而是因为它把一堵结构丰富的墙**压成了一个拍脑袋的标量**（`−1.0`、`≥5` 这些常数全靠手调、没标定）。idea graph 把墙的完整结构原样交给 LLM——能数的（入度、撞墙的是死 idea 还是活 idea）交脚本，该判断的（这堵墙到底有多硬、值不值得绕）交 LLM。

<details>
<summary><b>深挖：family / idea / insight 三层粒度、富图里铺了什么、成本为什么是闸门、三层奖励信号</b></summary>

**先分清三个粒度——选方向只在最粗的 family 层判断。** 上面的"家族"和后面要用到的 idea、insight 是三个不同粒度的东西，最容易混：

| | 是什么 | 类比 | 存在 wiki 哪 |
|---|---|---|---|
| **family** | 一**类** operator 方向（SA / PC / cross_dest…） | 老虎机的一只**臂(arm)** | `index.md` 的 family 分组 |
| **idea** | 这类里的**一个具体机制** | 这只臂上的**一种具体拉法** | `wiki/ideas/<slug>.md`（一思路一页） |
| **insight** | 跨多条 idea 的**硬约束/结论** | 一堵**墙**——"往这撞都会死" | `wiki/insights/<slug>.md` |

关系：**family ↔ idea 是 1 对多**（SA 这只臂下挂着 `sa-proposal-bias`、`focused-sa`、`sa-swap-2opt`… 好几条 idea）；**insight ↔ idea 是多对多**（一条 idea 可以撞好几堵墙，一堵墙也被好几个 family 的 idea 共享，如 `cb-mm-tradeoff` 横跨 SA/PC/CT）。两个最易混的区别：**idea 是"一条能去试的路"，有会迁移的状态（待试→主线/封死）、对应真实版本号和分数；insight 是"很多条路共同会撞死的原因"，是常驻约束，没有状态迁移。**

**为什么选方向只判断到 family、不下钻到 idea？** 细分到 idea 级每个只剩 2-3 个样本，任何"试得少就该探"的统计信号都会退化成近似常数、让所有没试过的 idea 并列顶格，跟随机选没区别。所以**选哪个 family 靠 LLM 读富图判断、选 family 里具体哪条 idea 靠因果推理**（看它撞不撞已知的墙），后者交给 wiki 查重而非打分。

**那选定 family 后，怎么挑里面具体哪条 idea？** 这是读图选 family 之后的一层（叫 Expansion），走的是另一套逻辑，先看岔路口：

```
idea_graph.py 富图 + LLM 探索/利用原则 → 选定 family X
                    │
        这个 family 有没有 dormant idea（status=待试）？
                    │
         有 ──→ 直接复活它（跳过造机制，进实现）
         无 ──→ Expansion 三步造新机制 → 进实现
```

- **有"待试"idea → 直接复活。** `idea_graph.py` 的 dormant 分桶会列出"仍开阔（未被死墙预言）"的待试 idea——这些此前已设计、记进了 `wiki/ideas/`，只是还没写代码。从"仍开阔"堆里挑一个进实现，不再发明新机制、也不再查重（建页时已查过）；"已被预言"堆的不碰。
- **没有 → Expansion 三步：** ① 读这个 family 里已封死 idea 死在哪堵墙上（看它们引用的 `[[insight:]]`，就是"已知雷区"）；② 新机制必须**绕开这些墙**，且得是结构性变化（改问题分解 / 引入全新组件 / 改优化目标建模 / 改信息利用方式），不能是调参/换序/换 gate 这种"伪切换"；③ wiki 按机制查重确认没以别名试过、不和已死方向共享高入度墙，通过才建新页、进实现。

**为什么这一层也不靠打分？** 一句话：family 级有 DAG 拓扑和死墙图可读，LLM 能顺结构判断；idea 级**样本太稀（每个机制 2-3 版）**，但"撞不撞已知墙"是**确定性**判断，比稀疏均值可靠得多。而且每入一条新 insight，多个机制"撞不撞墙"会同时翻转——所以机制级不固化成树，每轮现读 `wiki/insights` 临时推理。**"禁止伪方向切换"那条规则，本质就是 Expansion 阶段的剪枝器。**

这三个粒度怎么铺进富图：**idea 的 status/分数 → 染色每个节点的回报；idea 引用的 `[[insight:...]]` 边 → 算出每堵墙的入度、标出死墙传染；idea 的版本数 → 数出 family 的 `n` 和全场 `N`。** 脚本只把这些事实铺到图上，不合成任何裁决分。

**先验 vs 实测：LLM 怎么权衡新老家族。** 富图把每个 family 的"先验判断"（来自 wiki 跨思路硬结论 `[[insight]]`）和"实测涨跌"（活 idea 的真实分数序列）都铺出来，让 LLM 自己拿捏信哪个：一个家族刚开始试（`n` 小）时，实测样本太少、主要参考先验判断；试得多了（`n` 大），就主要信实测。这取代了 v0.0.1 里那条 `V=(1−w)·prior+w·observed`、`w=n/(n+k)` 的硬混合公式——同一个"老家族信实测、新家族信先验"的直觉，但权重不再拍一个 `k≈3` 的常数，而由 LLM 看着原始分布判断（公式会把一条 +0.42 的主线被同族一堆死机制的 −1 拉平，LLM 看原始序列不会）。

**成本是闸门，不是连续项。** 直觉上想把"改动成本"也塞进一个打分当减项，但那样会让"便宜但没用"的方向虚高。NOA 的做法是把成本当**闸门**：`cheap`（调参/改现有 operator）→ `medium`（加新 operator）→ `expensive`（全新组件/换框架/外部 solver）分档，expensive 档仅当所有便宜档都试穿才考虑——成本只决定"什么时候轮到它进场"，不折算成分数排序。

**实测回报按可信度分三层（喂给 LLM 看的原始信号，不合成标量）：**
1. **线上 Δ**（最可信）——这版真提交了，有线上分差。
2. **本地 Δ + 转化率心智**——只有本地分差时，要记得打折看。这个折扣是吃过亏定下来的：v318 本地涨 +0.20、线上只涨 +0.01，约 5% 转化率，所以本地涨分要大打折扣才能当真。
3. **status 兜底**——连本地分差都没有，就看 wiki 里这条思路的状态（主线/部分有效/封死）。

v0.0.1 把这三层硬合成一个 `observed` 标量喂进公式；v0.0.2 直接把三层原始信号都铺在富图上，由 LLM 分辨"这条 +0.5 是不是早期弱基线虚高"——这正是标量公式看不出、要换成 LLM 判断的那类事实。

**先验的跨臂隔离仍成立：** 一个家族的先验判断只来自它自己的历史，不会被别的家族的成败串味——避免"隔壁那条路火了，连带高估这条"。

阶段自检每轮会跑 `idea_graph.py` 打印一行状态条，报当前家族的 `n`/cost/活 idea 数和图上还有哪些更开阔的方向；当前家族已挖透、或更值得探的方向出现时，提示该换方向了。"连续 5 轮无正增量"退化为**保底提醒**——不再是唯一开关，死墙剪枝和 exploit 收益判断会更早把动力转向 explore。

**family 集合本身会变吗？——只增不裂。** 上面讲的都是在一个**固定的 family 集合**里选，分两面看它怎么松动：

- **能新增（探索一只全新 arm）。** 已知 family 可能被同一组 insight 墙集体封顶——这时图内怎么跳都跳不出去。出口是**文献搜索**（成本梯子的最顶档 `cheap→medium→expensive→文献`）：当**所有**已知 family 都走不通（连 `n=0` 的开阔 family 都试穿、dormant 全被死墙传染剪掉、没有任何活 idea 仍在涨）才解锁，去图外找能绕开 `cb-mm-tradeoff`、`global-state-propagation` 这类高墙的新算法范式（LP / min-cost flow / matching…），**当作一个新 family 接进 `wiki/ideas`**。脚本侧是平滑的：新 family 天然 `n=0`、富图里直接显示为"从没看过的开阔方向"自动排到 explore 的最前（你刚付了搜文献的贵成本，本就该先试它），脚本对未知 family 名兜底处理、不用改任何种子表。
- **不该按参数劈裂。** 直觉上 SA 攒了 6 条 idea、行为差异很大，想拆成 SA-温度 / SA-提案 / SA-邻域——但那等于把一只样本充足的 arm 切回稀疏 arm，正好打破 family 存在的前提（family 级平均十几版、回报判断才有意义；细分后每档剩 2-3 版，"没试过"信号主导 = 随机选）。family 内部的异质性不在选 family 这层拆，而在 Expansion 层用因果处理：只看活 idea 的回报、死的不拖累，选具体子机制靠撞墙剪枝。

所以 family 集合**只增不裂**——增长靠文献搜索从图外接全新 arm，绝不靠把现有 arm 切细。

</details>

### 5.3 wiki 记忆层

**一句话：** 把"事实"和"判断"分开存，让 NOA 记得哪条路试过、为什么死，下次产方向前先查，不再重复撞墙。

> 这套机制借鉴了 Karpathy 的 [LLM wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) 模式：让 LLM 增量维护一个持久、互相链接的 markdown wiki，作为"会复利增长的知识沉淀物"夹在你和原始资料之间——不像普通 RAG 每次都去重查原文，而是把知识编译一次、之后持续保鲜。NOA 把它落到算法迭代场景：原始资料是每版的分数与日志，wiki 沉淀的是"哪条思路通不通"的判断。

最大的浪费是失忆：同一个死胡同，这次撞了下次还撞。NOA 用一个 `wiki/` 目录当长期记忆，里面装的是上百版迭代攒下的**判断**，沉淀成两类可检索的页：

- **`ideas/`（当前 44 条思路页，一思路一页）**：每页记这条思路的**状态**（主线 / 部分有效 / 待试 / 封死）、关联的**版本外键**（`v236`、`v250`… 指回 SCORES 的事实行）、线上/本地分、**死因**，以及**思路之间的边**（A 启发了 B、C 取代 D、E 和 F 互斥）。
- **`insights/`（当前 27 条跨思路硬结论）**：不绑定单条思路、被反复验证过的规律——比如"本地涨分约 5% 转化到线上""SA 搜索空间已挖尽"。

外加 `index.md`（按状态/family 分组的目录）和 `log.md`（时间线 + sync 水位）。靠**两条分界线**保证它不烂：

- **事实 vs 判断分开。** 分数、日志、提交记录这些"客观发生过的事"写在 `SCORES.md` / `logs/`（事实层）；"这条路通不通、为什么、现在是主线还是封死"这些"判断"写在 `wiki/`（判断层）。两边不重复——事实变了不用动判断，判断变了不用动事实。
- **按机制检索，不按文字。** 查"这路试过没"，比的不是标题字面像不像，而是**底层机制**是不是同一回事。换个说法重新包装的老死路，照样能被认出来。

每轮迭代结束，新版本的判断会被沉淀回 wiki：这版属于哪条思路、verdict 是涨是退、状态怎么迁移（待试→封死 / 新增主线）。产新方向前，先查 wiki 确认不是在重走死路。

**和选方向的关系：wiki 不只是给人查的，它是 [idea graph 选方向](#52-idea-graph-选方向)的结构化输入。** [`idea_graph.py`](.claude/skills/algorithm-iterate/scripts/idea_graph.py) 每轮直接解析 `wiki/ideas/*.md` 的 frontmatter，把判断铺进富图：

- **`status`** → 染色每个 idea 节点（主线 / 部分有效 / 待试 / 封死），也用来区分一个 family 是"还活着"还是"整条都封死了"。
- **`[[insight:...]]` 边** → 算出每堵 insight 墙的入度、标出死墙传染：撞到高入度"封死墙"的方向会被剪枝，挂着"还有空间"类 insight 的方向值得探。那条 5% 转化率的教训（来自 [`local-online-divergence`](wiki/insights/local-online-divergence.md) insight）正是这么进到本地 Δ 折扣里的。
- **`versions` 外键** → 数出 `n`（family 试了几版）和 `N`（全场总版本数），决定一个 family 在图上算"挖透了"还是"还开阔"。

于是闭环成立：**wiki 沉淀判断 → idea_graph 把判断铺成富图 → LLM 读图挑方向 → 跑出新版本 → 判断再沉淀回 wiki**。第 5.2 节那套"先验 vs 实测"的权衡，先验那一半的数据源就是这里。

<details>
<summary><b>深挖：比 grep 省在哪（实测）、sync 水位对账、判断不外包</b></summary>

**为什么不直接 grep logs，要单独编译一层 wiki？** 我们在 skill workspace 做过一次消融：拿 3 个真实查重问题（"分两阶段先压 MM 再降 CB 试过没""给 SA 提案加 prefport 偏置呢""初始解能不能用 min-cost flow"），对比两条路——**查 wiki** vs **禁用 wiki、退回去翻原始 `SCORES.md` + `logs/`**。

两条路**答案完全一样**（3/3 命中、同样的证据版本、同样的死因）——所以差的不是对错，是**成本**：

| | 查 wiki | 退回翻 logs |
|---|---|---|
| 平均 token | **30.7k** | 41.8k |
| 要啃的原始文本 | index（97 行）+ 1-2 页 idea | `SCORES.md` 81 行 + `logs/` 4490 行（~271KB） |

平均省 **27% 的 token**（单题最高省 43%），要扫的原始文本差约 **45 倍**。

省在哪很关键：**省的不是 grep 那一下，是 grep 之后那一大片**。`logs/` 按"天"存事件流，而查重按"思路"问——两根轴是垂直的，一条思路（比如 `sa-proposal-bias`）跨好几天连载，grep 只能定位到一行，但状态/线上Δ/死因都写在命中行前后的叙事里，于是 grep 完必须 read 一片；措辞不撞词时（查的人说"压最大负载"、日志写"MM/sa_max"）grep 直接失灵，被迫整天通读；最后还要"确认没漏报"——否定命题没法用 grep 证明，只能过度读来防漏。**wiki 把这三笔开销一次性预编译掉了**：把存储轴从"按天"转成"按思路"，查询就从"横扫 N 天现场综合"塌缩成"index 定位→读 1-2 页"。历史越厚，杠杆越大——翻 logs 的成本随版本数线性涨，查 wiki 基本恒定。

**sync 水位对账：** 事实层（SCORES/logs）和判断层（wiki）是两套文件，靠 `log.md` 里的一个"水位线"对账——记录 wiki 已经消化到哪个版本了。新提交的版本如果还没沉淀进 wiki，水位线就落后，自检时能发现"有 N 个版本的判断还没记"，提醒补上。这样两层不会悄悄失同步。

**事实/判断的真相源边界：**

| 问题 | 去哪查 | 不去哪查 |
|------|--------|----------|
| 这版线上多少分 | `SCORES.md` / `online_ledger.md`（事实层） | 不去 wiki（判断层可能滞后） |
| 这条路为什么死的 | `wiki/ideas/<slug>.md`（判断层） | 不去 logs（事实层不存因果判断） |
| 现在主线是哪条 | `wiki/index.md` | — |

判断写进 wiki 的活由 wiki ingest subagent 按主线给的 spec 执行（见 [5.1](#51-主线-orchestrator--4-个-ephemeral-subagent)）——主线先定好 verdict、思路归属、状态迁移这三件"判断"，subagent 只负责按 spec 敲字，不自己下判断。

</details>

### 5.4 分层数据集 (Layered Datasets)

**一句话：** 线上真值太贵（不可逆、要人肉、稀缺），只能靠本地分代打——所以把本地集按"和线上的相关性"分层，再让它跟着线上反馈自己进化，越用越像线上。

整个迭代闭环的判断都建立在一个假设上：**本地分能代表线上分。** 可这个假设天然不牢——v318 本地涨 +0.20、线上只涨 +0.01。一个 case 集合在本地把版本排出来的名次，和线上未必是同一个名次。如果不治理，agent 会朝着"本地好看"自欺。NOA 的办法是**不把本地集当成一个整体**，而是按各自和线上的关系切成多层，每层只干一件事：

| 层 | 角色 | 怎么用 |
|----|------|--------|
| `submit_core` / `backbone` | **主排序骨架** | 决定一版到底值不值得提交——core 真涨才是绿灯 |
| `submit_anchor` | **反向诊断** | 已知低转化的家族；它独涨或涨得比 core 还猛 = **红灯**（不是加分项） |
| `prefport_veto` | **硬否决** | 不参与排序，但跌破基线 = 直接否掉这版，不管别层多好看 |
| `guardrail` | **鲁棒性闸** | 防 timeout / 极端退化，单 case >7.4s 才关注 |
| `transfer_holdout` | **低置信告警** | 近邻版本若只在这层涨、骨架没动 → 标记为低置信提交 |
| `candidate` | **观察验证层** | 新造的 case 先落这里，攒线上反馈，暂不参与主排序 |

关键设计：**这些层的含义是"反"着用的也有**——`anchor` 独涨是红灯、`candidate` 独涨却是探索性正信号。一个本地涨分，落在不同层里，结论可能完全相反。这正是"本地分会骗你"的解药：不信任单一汇总分，而是看涨在哪一层。

**让分层自己进化的两个卫星 skill。** 分层不是一次定死的，它跟着线上反馈长——靠主循环之外的两个 skill：

- **`generate-dataset`（造新 case）**：当现有 case 在好/差算法之间拉不开差距（多版同分、或本地排序和线上相反），说明覆盖有盲区。这个 skill 按"哪个指标能把算法质量差异暴露出来"去设计结构性的新 case（不是调数值范围），新 case 默认落 `candidate` 观察。是**无中生有**。
- **`calibrate-dataset`（按相关性重分层）**：每攒满 **3 次新线上提交**触发一次。它重跑 `submit/` 里归档的历史 solver，重建**逐 case 粒度**的"candidateΔ ↔ 线上Δ"配对——稳定正相关的 case 晋升 `submit_core`，稳定反向的移去 `contrast` 当反向指标，噪声的留在 `candidate`。是**分存量**，不造新 case。

于是又一个闭环成立：**generate 造 case → 进 candidate 观察 → 攒够 3 次线上反馈 → calibrate 按真实相关性重分层 → 主排序集越来越能预测线上。** 本地分不是静态的尺子，而是一把会自己校准的尺子。

<details>
<summary><b>深挖：为什么校准要逐 case 而非总分、线上分为什么单独建台账</b></summary>

**校准的核心是逐 case 配对，不是看 candidate 总分。** 总分会互相抵消——三个 case 一个 +0.3、两个 -0.15，总分还是涨，但你不知道是哪些 case 在真预测线上。`calibrate-dataset` 重跑相邻提交版本的归档 solver，对 candidate 的**每一个 case** 取版本间分差，再和台账里对应的线上Δ逐个对齐，按同号/反号的稳定程度归类。05-31 那次校准就是靠逐 case 可靠性打分做的，不是总分。

**线上分单独建台账（`online_ledger.md`），因为它是唯一本地不可复算的数据。** submit_core、candidate 的总分和逐 case 分，都能拿 `submit/` 里归档的 solver 重跑得到；唯独线上分来自线上评测机，本地永远算不出。所以台账只 durably 记三样必填：**线上分、线上Δ、配对的归档 solver 文件名**——其余快照列可空，校准时用归档 solver 重跑补全。这也是为什么"每次线上提交必须把对应 solver 复制进 `submit/`"是硬规则：漏归档 = 那一版再也无法参与逐 case 校准。

**防过拟合的护栏。** 不足 3 次提交不校准（样本太少，重分层是噪声）；`anchor` 只做反向诊断、不作正向佐证；`prefport_veto` 是不参与排序的硬否决层。多层口径互相制衡，避免 agent 把本地集优化成一个只对自己有意义的过拟合靶子。

</details>

## 6. 成绩进展 (Score Progression)

从最初的 round-robin 基线一路爬到接近第一名。下面是有代表性的里程碑版本，标了每版属于哪个**家族**、主要在攻哪个**指标**（完整排行榜见 [SCORES.md](SCORES.md)）：

| 版本 | 线上分 | 家族 | 主要提升 | 关键改动 |
|------|--------|------|----------|----------|
| v1 | 276 | — | 基线 | round-robin |
| v8 | 347 | 初始解 | 整体结构 | per-flow 逐流独立选端口（+21） |
| v43 | 359 | portfolio | 候选多样性 | 3 策略 ensemble |
| v62 | 366.25 | 比较器 | MM / 瓶颈 | 词典序比较器 jm→fg→ci→future（优先压最大负载） |
| v138 | 369.12 | PC | CB（相位间 Cbtphsc） | score-aware 端口一致性 + 全局压力 tie-break |
| v232 | 369.65 | SA | CB（退火降冲突） | SA 退火预算收紧 |
| v292 | 369.73 | SA | CB（高冲突卡聚焦） | 三轮 focused SA + cross_dest 恢复 |
| v369 | 369.86 | cross_dest | CB（任务间 Cbttskc） | cross_dest top-3 混合打分 |
| v430 | 369.89 | pipeline | 运行预算（解锁大 case 后段） | time_tight 阈值放宽 4.5s→7.0s |
| **v454** | **370.15** | **global_state** | **MM（global_out 准确性）** | **actual global_out + CB-aware 贪心 portfolio** |

> **MM** = 最大负载瓶颈（评分公式里的 `40/Maxsingler + 40/Maxmultir` 项）；**CB** = 冲突罚分（`Cinphsc/Cbtphsc/Cbttskc` 三类，权重 12/5/3）。这两个是评分公式仅有的两大杠杆。

**看家族+指标能看出一条清晰的弧线：** 早期（v8–v62）靠结构性改动和压 MM 拿大头；一旦 MM 触到信息论下界、再压不动（见 wiki insight [`proxy-at-info-bound`](wiki/insights/proxy-at-info-bound.md)、[`mm-tight-bound-unreachable`](wiki/insights/mm-tight-bound-unreachable.md)），中后段（v138–v369）几乎全是在不同家族里换着法子降 **CB**——PC 降相位间冲突、SA 退火降冲突、cross_dest 降任务间冲突。最后 v454 又回到 MM，但走的是"把 global_out 的保守近似换成真值"这唯一一道还没堵死的缝，而不是硬压。

**当前最佳：370.15（v454），最终排名27（三等奖）。**（注：这个分数是w/o wiki和ucb的NOA版本获得的）

一个值得记的教训藏在 v318：本地涨了 +0.20、看着是绿灯，线上只涨 +0.01——约 5% 的转化率。这条经验后来沉淀成 wiki insight [`local-online-divergence`](wiki/insights/local-online-divergence.md)，喂进[选方向](#52-idea-graph-选方向)时让本地分差要打折才能当真（v0.0.1 时是 UCB 公式里的一个折扣项，v0.0.2 改由 LLM 读富图时按转化率心智判断）。
