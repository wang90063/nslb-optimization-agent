### v369 audit: 基线更正与 gate 叶子审计

**思路：** 先确认当前 `Solution.cpp` 是否仍是线上最佳 `v369`，再重新审查 `p32/r4` 主窗口上各叶子结点真实覆盖到的 operator，避免继续沿着旧基线结论迭代。

**实现：** 将 `Solution.cpp` 同步回 `Solution_20260528_v369_crossdest_price_mix.cpp`，并用 `tmp_gate_audit_v369.cpp` 在不改协议输出的前提下记录 `time_tight`、`any_jm_le_r`、`enable_r4_makeroom`、`global_price` 等 gate 命中情况。

**结果：**

| submit_core | 556.63 | 560.09 | +3.46 |

- `proxy_8`：`tight=0 anyjm_yes=19 anyjm_no=1 r4_jobs=20 r4_fg32=0 r4_sizeok=20 r4_mr=0`
- `online_8`：`tight=7 anyjm_yes=33 anyjm_no=0 price_eligible=40 price_blocked_tight=7 r4_fg32=0 r4_sizeok=38 r4_mr=0`

### v390: cross_dest 全域 phase-aware target ranking

**思路：** `v369` 的 `cross_dest` 候选 port 排名仍是“整卡总 count + price mix”。尝试把 pair/single-flow 两条分支都改成 phase-aware 排名，让 flow 更优先追随自己覆盖 phase 上已经常用的 port，而不是整卡全局 dominant port。

**实现：** 基于 `v369` 新建 `Solution_20260530_v390_crossdest_phaseaware.cpp`：
- 新增 `cross_dest_phaseaware_score(card, sl, dl, mask, pk, m)`
- 候选 port 打分从 `dp_cnt*256-joint_price_bias(...)` 改成 `exact_support*512 + total_support*32 - joint_price_bias(...)`
- pair 和 single-flow 两条 `cross_dest` 分支同时切换到这套排序

**结果：**
| 数据集 | 旧 | 新 | Delta |
|--------|---:|---:|------:|
| submit_core | 560.09 | 559.37 | -0.72 |

补充现象：
- `proxy_3` 运行到 `704.989s`，直接出现超长退化
- 这说明 phase-aware 排名一旦全域替换，会把原本稳定的 `p16` `cross_dest` 路径也一并扰乱

**结论：** 这不是可接受的主线方向。phase-aware 信号不能直接全域灌进 `cross_dest`，否则会放大 `p16` 路径的搜索成本和错误 move。

### v369 code audit: 代码叶子表与阈值泛化风险

**思路：** 不再从 testcase 反推，而是直接从 `v369` 代码树出发，把 `solve_job()` 和关键 operator 的 gate 统一整理成“宏叶子 / 微阈值 / operator 覆盖 / 泛化风险”表，判断问题到底是“漏叶子”还是“叶子被 magic number 切得太碎”。

**实现：** 逐段审查 `solve_job()` 的主 gate（`time_tight / huge_job / any_jm_le_r / global_price / allow_extra_pc_chain / r4 make-room / low-r family`），以及 `run_port_consistency_perport_refine()`、`run_cross_dest_swap()`、`run_cbttskc_reduce()`、`run_sa_*()`、`run_lowr_*()` 各自的内部阈值。

**结果：**

代码宏叶子表：

| 宏叶子 | 结构条件 | 微阈值 / 子切片 | 实际覆盖的 operator | 泛化风险 | 判断 |
|--------|----------|-----------------|---------------------|----------|------|
| `time_tight` 叶子 | `g_job_idx>0` 且触发性能门控 | `proj>4.5` 或 `el>3.0 && fl_count>20000` | 只保留 S1-S3；跳过 S4-S18；`PC` 迭代变短；`cross_dest` 迭代降到 1；无 `CT/SA/SA-swap` | 极高 | 当前最脆弱的大叶子；不是只砍一个 operator，而是整段砍尾链 |

| 类型 | 典型阈值 | 泛化性判断 |
|------|----------|------------|
| 结构性阈值 | `g_r<=3 / g_r==4`、`g_p<=16 / g_p>=32`、`jm<=r / jm==r+1 / jm>r+1` | 相对稳定，属于问题结构，不是主要风险 |
| 形状窗口阈值 | `fl_count<=4500/5000/5500/6000/7000`、`job_work<=40000/70000/80000/100000/120000/150000`、`m>=17`、`fg>=32` | 泛化风险高，很多是从已有 case 的收益/超时对抗里调出来的 |
| 运行时反馈阈值 | `proj>4.5`、`el>3.0 && fl_count>20000` | 风险最高，受机器、顺序、隐藏集 job mix 共同影响 |

几个关键来源：
- `time_tight` 来自 `v199` 性能门控试验
- `50000~80000 + fl_count<=5000` 这组 shape gate 来自 `medium_25/32` 对 `AI33` 的收益/超时对抗
- `r4 make-room` 的 `4500/40000/fg>=32` 来自 `v212` 对窄 `r=4` 结构的人工收窄

**结论：**
- 现在的主要问题不是“完全漏掉某个 testcase family”，而是一些大叶子被很多经验阈值切成了脆弱子叶。
- 最脆弱的三处是：`time_tight`、`allow_extra_pc_chain` 的 size 窗口、`r4 make-room` 的白名单窗口。
- `low-r` 那一整族反而相对更结构化；真正不稳的是 `r=4` 大叶子，尤其是 `p32/r4` 和 `p16/r4`。
- 后续如果继续迭代，不应再优先做“微调阈值”；更合理的方向是：
  1. 提升 cheap path 的 operator 质量，让 `time_tight` 叶子本身更强；
  2. 让 `p32/r4` 的主族减少对 `fl_count<=7000` / `fg>=32` 这类小窗的依赖；
  3. 尽量把绝对值 gate 换成更连续、可归一化的指标，而不是继续堆新的 magic number。

### v392: `p32/r4` `global_price` leaf 内 lex compare

**思路：** 既然 `v388-v391` 证明 gate surgery 和 `cross_dest` rerank 都不是正路，就不再碰 gate，只改 `p32/r4` 主叶子里 `global_price` 的候选比较方式。目标是把它从单个线性 cost 改成更接近 `better_metrics` 的分层比较，让 `jm/fg/overflow` 先决定结构，再用历史 price 做后段 tie-break。

**实现：** 基于 `v369` 新建 `Solution_20260530_v392_global_price_lex_p32.cpp`：
- 新增 `GlobalPriceChoice` 和 `better_global_price_choice_p32r4(...)`
- 仅在 `run_greedy_global_price()` 的 `g_p>=32 && g_r>=4` 分支启用新比较器
- 比较顺序改为 `score_jm -> score_fg -> local_over -> future_over -> price_bundle -> future_sq -> future_sum`
- 其中 `score_jm/score_fg` 仍按 `<=r` 压平，避免在线容量内过度追逐更小的局部 load

**结果：**
| 数据集 | 旧 | 新 | Delta |
|--------|---:|---:|------:|
| submit_core | 560.09 | 560.10 | +0.01 |
| submit_anchor | 266.47 | 266.67 | +0.20 |
| contrast | 575.08 | 575.07 | -0.01 |
| prefport_veto | 389.05 | 389.02 | -0.03 |
| guardrail | 413.73 | 413.79 | +0.06 |

代表性 case：

- `online_7`：`Maxmultir 8.75 -> 8.50`，总分 `63.77 -> 63.87`

## Operator 质量改进计划（Direction H）

**核心原理**：v369 证明"改 operator 内部 move 质量"能以 ~10% 转化率转线上。当前 11 个 post-processing operator 中，只有 `cross_dest_swap` 使用了 `joint_price_bias`。其余 operator 的 move-level 决策完全不感知跨 job 历史信息。

**按高频→大规模排序**：

| # | Operator | 频率 | 当前决策 | 改进方向 |
|---|----------|------|---------|---------|
| 1 | run_port_consistency | 每 job 5 iter | target port: min Cbtphsc, tiebreak=global_out+global_in | 在 pressure 相等时加 price_term 第三级 tiebreak |
| 2 | run_relaxed_swap | 每 job 5 iter | 纯 Cbtphsc，无 tiebreak | dl_i≠dl_j 时用净 price 变化做 tiebreak |
| 3 | run_sa_composite | 每 job 3 pass | 随机选 port | 50% 随机 + 50% bias 向低 price port |
| 4 | run_cbttskc_reduce | 每 job 3 iter | wt=3*ct+5*cbt-12*ov | 加小权重 price_bonus 项 |

**不做的事**：
- 不改 neutral_swap（同 sl/dl 的 swap 净 price 变化恒为零，数学上无意义）
- 不改 run_swap / run_global_swap / run_lns（主目标是降 jm/fg，price 干扰大）
- 不改 portfolio 选择规则（v404 已证明不转化）

**v409 失败教训**：
- neutral_swap 的 tiebreak 数学上无意义（同 sl/dl swap 净 price = 0）
- relaxed_swap 的公式方向搞反了
- PC 的 pressure 直接替换为 joint_price_bias 量级不匹配
- 正确做法：只在"原本无差别"时加最小侵入的 tiebreak，不替换已有逻辑
