### param_extreme_r2 深度分析

**结构**：n=40, l=100, p=32, r=2, total_flows=3785, m∈[8,16], f∈[66,141]

**瓶颈根因**：
- Leaf 47 是最热叶子：总负载 180，被 26 个 job 触及
- 5 个重 job (12,17,20,28,38) 在 leaf 47 上有 247-387 flows，使用全部 32 端口
- Phase 约束 (r=2) 导致部分端口 max-phase-load=2（而非理想的 1）
- 5 个重 job 各贡献 ~2 到某些端口，累积到 7 而非最优 6
- 端口分布：[7×12, 6×20]，最优应为全部 5-6 (180/32=5.625)
- 当前 MM=3.50 (7/2)，最优 MM=3.00 (6/2)

**为什么现有算法解决不了**：
- 结构性下界 MM=3.00 需要所有端口 ≤6，但 phase 约束使得重 job 必然在某些端口产生 max-phase-load=2
- 5 个重 job 各自独立最优，但累积效应导致全局次优
- 单 flow swap 无法改善：热端口 load=7，移走一个 flow 到 load=6 的端口会使目标端口变 7
- 这是跨 job 累积问题，不是单 job 内部问题

**线上约束确认**：
- 线上评测是**交互式**：每个 job 到来时必须立即决策，不能回溯
- 方案 1（全局优化/读所有 job）：不可能
- 方案 2（多 pass）：不可能
- 唯一可行方向：在顺序决策框架内做更好的选择

### v206 Global 2-opt 实验

**思路**：在 `run_global_swap`（单 flow 移动）之后加 2-opt swap，交换热端口和冷端口上的两个 flow，期望减少 future_gmax。

**实现**：
- 找到 gmax 瓶颈 (leaf, port)
- 遍历热端口上的 flow i 和其他端口上的 flow j
- 尝试交换：i→j的端口，j→i的端口
- 约束：不恶化 jm (≤pre_jmax)
- 接受条件：future_gmax 严格下降

**结果**：

| 版本 | submit_core | 变化 |
|------|-------------|------|
| v199 | 1086.20 | baseline |
| v206 | 1084.28 | **-1.92 退化** |

**逐 case 分析**：
- param_extreme_r2: 57.62→57.62（**无变化**，2-opt 找不到有效交换）
- medium_25: 64.29→63.51（-0.78，2-opt 破坏了端口一致性）
- param_p32_r4_n40: 69.28→68.61（-0.67）
- proxy_3/5/6/7: 小幅退化 (-0.04~-0.09)

**失败原因分析**：
1. **jm 约束过严**：热端口已有 cell=jm，任何 flow 移入都会违反约束，导致 2-opt 在目标 case 上找不到合法交换
2. **破坏端口一致性**：在其他 case 上，2-opt 虽然降低了 gmax，但打乱了 flow 的端口分配，使后续 Cbtphsc 优化效果变差
3. **O(n²) 复杂度**：对大 job 增加了运行时间，可能触发 time_tight
4. **根本矛盾**：要降低 gmax 就需要降低热端口的 max-phase-load，但 max-phase-load=jm，降低 jm 是另一个独立的难题

**结论**：2-opt swap 在当前框架下不可行。gmax 的瓶颈本质上是 jm 的累积效应，不是单 job 内的局部最优问题。

### v214 不转化原因定位

1. `submit_core` 的 `+0.3035` 几乎被 **2 个 low-r param case** 吃掉了：

   - `proxy`: 总和 only `+0.0265`
   - `medium`: `+0.2132`，但核心是 `medium_31` 这个 low-r case
   - `lowr`: `+0.2464`
   - `param`: **总和 `-0.5340`**
3. 最关键的隐藏负样本不是“全面退化”，而是**同一种错误交易反复出现**：
   - `param_r3_p16`: `70.52 -> 69.44`，`MM 3.33 -> 3.67`，同时 `CBT 783 -> 727`
   - `lowr_2`: `50.63 -> 50.27`，`MM 6.50 -> 7.00`，同时 `CBT 4030 -> 3759`
   - `adversarial_cumulative_pressure`: `61.60 -> 61.54`，`MM 12.50 -> 12.75`，同时 `CBT 139 -> 134`
   - `bench_4`: `61.88 -> 61.87`，`MM 14.25 -> 14.50`，同时 `CBT 5091 -> 4556`
4. 这说明问题不是 gate 太宽，而是 **gate 内 top-2 make-room 的接受准则只看 `CBT` 改善，不看 global future safety**
   - 当前选点逻辑本质上是：谁的 `Cbtphsc net gain` 更大就优先谁
   - rollback 只挡住了“当前 job 的 `fg/jm` 立刻变坏”
   - 但它**没有挡住**“把 flow 挪到历史更热的 port 上，在 `fg` 持平时悄悄恶化未来累积 `MM`”这类交易
5. 因此，`v214` 没有线上转化的最直接解释是：
   - 本地主集把 `r2/p32` low-r 收益看得过重
   - 同时缺少 `param_r3_p16 / cumulative_pressure` 这类“`CBT` 变好但未来 `MM` 变差”的反例
   - 结果是版本在本地看起来净增，但线上更相关分布里被这些 hidden negative 抵消

### v222-v224：直接改候选解形状，但还没长成主线

目标：不再继续磨 make-room 小 gate，直接改 **候选解质量 / 初始分配形状**，验证能否真正打到 `proxy_3 / proxy_5 / medium_32 / param_p32_r4_n40` 这类 future-pressure case。

1. `v222`：pressure-order 初始候选族
   - 思路：把 flow 顺序从“输入顺序/反序/随机”改成 **热点叶子 + 重 mask flow 优先**，再交给 `hardcap / FTRL / fgmax` 三类 greedy
   - 结果：
   - `submit_core`: `956.96`（vs `v221` 的 `957.97`，**-1.01**）
   - 固定对抗集：`510.04`（vs `v221` 的 `510.66`，**-0.62**）
   - 正信号：
   - `medium_32`: `63.17 -> 63.24`，`MM 9.50 -> 9.25`
   - `medium_25`: `64.29 -> 64.39`，`MM 7.75 -> 7.50`
   - 负样本：
   - `param_p32_r4_n40`: `69.28 -> 68.62`，`MM 3.75 -> 4.00`
   - `param_n40_hot`: `59.82 -> 59.35`，`MM 4.50 -> 4.75`
   - `proxy_3`: `37.85 -> 37.83`
   - 判断：**全局 hot-flow 排序** 确实能动到大 `p16/r4` case 的 `MM`，但会把 `p32` 和中等 proxy 结构一并压坏，泛化不够
2. `v223`：把 hotleaf coordinated rebuild 放宽到 `r=4/p>=16`
   - 思路：不改 greedy，只扩“最热叶子局部协同重排”这个 operator 的适用范围
   - 结果：
   - `submit_core`: `957.96`（vs `v221`，**-0.01**）
   - 固定对抗集：`510.65`（vs `v221`，**-0.01**）
   - `medium_32`: `63.17 -> 63.16`
   - 判断：这条 operator 在 `r=4` 上基本**没有新信号**，说明 low-r hotleaf rebuild 不是当前主线缺的东西
3. `v224`：pressure-order 升级成完整 global family
   - 思路：不让“生的排序解”直接入选 portfolio，而是作为完整策略：
   - `pressure-order seed -> run_swap -> run_global_swap -> run_lns -> TRY_STRATEGY`
   - 结果：
   - `submit_core`: `957.27`（vs `v221`，**-0.70**）
   - 固定对抗集：`510.13`（vs `v221`，**-0.53**）
   - 正信号更强：
   - `medium_32`: `63.17 -> 63.35`，`MM 9.50 -> 9.00`
   - `medium_25`: `64.29 -> 64.39`，`MM 7.75 -> 7.50`
   - 但关键负样本仍更大：
   - `param_p32_r4_n40`: `69.28 -> 68.61`，`MM 3.75 -> 4.00`
   - `proxy_7`: `65.90 -> 65.61`，`MM 5.75 -> 6.00`
   - `proxy_3`: `37.85 -> 37.82`
   - `bench_1`: `69.12 -> 69.10`
   - 判断：即使配上 `global_swap + lns`，**pressure-order family 仍然只讨好大 `p16/r4` case**，没法跨 family 转成主线
4. 本轮结构结论：
   - 当前缺的不是“更激进地把热 flow 提前处理”，而是**既能识别大 `p16/r4` future-pressure，又不会把 `p32` / 中等 proxy 结构过度压扁的 candidate family**
   - 这三条更大结构线都**不替换 `Solution.cpp`**，但它们把一件事说清楚了：`medium_32/25` 和 `param_p32_r4_n40 / proxy_3/7` 之间存在真实结构分歧，后续主线不能再用单一 pressure-order 去硬吃
   - 研究底座仍保持 `v221`

### v225-v226：专门围绕 `param_p32_r4_n40` 拆根因

目标：把 `pressure-order` 为什么稳定压坏 `param_p32_r4_n40` 这件事拆透，再看是否能保住 `medium_32/25` 的收益同时避开 `p32` 退化。

1. 现象拆解：
   - `v221` 在 `param_p32_r4_n40` 上是一个**超大平顶**：
   - `raw_max=15 (MM=3.75)`，但 `at_max` 非常多（按方向计数约 `1540` 个 cell 在 15；按 `(leaf,port)` 聚合后也有 `905` 个）
   - `v224` 则把它压成了少数尖峰：
   - `raw_max=16 (MM=4.00)`，只剩 `5` 个 cell 顶到 16
   - 新的尖峰集中在：
   - `out leaf=5 port=0/1`
   - `in leaf=13/15/17 port=0/1`
   - 并且这些尖峰共享大量相同 job（例如 `j0/j3/j5/j11/j30/j35/j39` 反复重合）
   - 结论：这里不是“未来压力判断错了”，而是 **pressure family 把原本平的 32 端口平台压成了少数相关性很强的尖峰**
2. 结构对比：
   - `param_p32_r4_n40` 的 case-side `future_fg` 原始下界只有 `13`，当前 `v221` 做到 `15`
   - 但它的热点是**分散的、宽端口的、平台型**；不像 `medium_32` 那样有少数特别重的热点叶子：
   - `medium_32` 原始下界 `36`，而 `v221` 仍在 `38`
   - `proxy_3 / proxy_7` 虽然也可能有高 `raw_lb`，但它们在 `v221` 已经达到 `MM` 下界，继续 reshaping 只会换来冲突或 future 回退
3. `v225`：pressure-order family + port permutation 去相关
   - 思路：保留 `pressure-order` family，但把端口扫描从固定 `0..p-1` 改成带 `job_idx/sl/dl/mask` 的 rotation，试图打掉 `p32` 端口共振
   - 结果：
   - `param_p32_r4_n40`: 仍是 `68.60`，`MM 4.00`
   - `medium_32`: 回到 `63.18`，`MM 9.50`
   - `submit_core`: `957.23`
   - 结论：**不是简单的低编号端口偏置问题**；去相关 rotation 既没救回 `p32`，也把 `medium_32` 的收益丢了
4. `v226`：pressure family 只在“当前 best candidate 不是大平台”时放行
   - 思路：基于 `v221` 的 best state 形状加 gate：
   - 只有 `best_eval.fg > future_fg_lb` 且 `max-cell 平台不大` 时，才运行 pressure family
   - 目的是排除 `param_p32_r4_n40` 这种“本来就是大平台”的 case
   - 结果：
   - `medium_25`: `64.29 -> 64.30`
   - `proxy_3 / proxy_7 / proxy_8`: 回到 `v221`
   - 但 `param_p32_r4_n40` 仍然是 `68.61`，`MM 4.00`
   - `medium_32` 也没有保住 `v224` 的 `9.00` 收益，回到 `63.16`
   - `submit_core`: `957.30`
   - 结论：单靠“平台 gate”也不够，说明 **同一 family 在 job 级时序上仍会提前把结构带偏**，不是只看最终 best-state 平台大小就能裁掉
5. 新结论：
   - `param_p32_r4_n40` 这类 `p32/r4` case 的核心不是“压力不足”，而是 **宽端口对称结构对跨 job 相关性非常敏感**
   - 因此后续如果还要做 future-pressure family，不能只靠全局排序 / reshaping / 末端 gate 修补；需要从**候选生成时的跨 job 去相关**或**完全独立于 pressure-order 的新 family**切入
   - 到这里为止，`pressure-order` 这条主思路已经基本被证伪为当前主线方向

### v227-v228：`plateau32` 专项 family 仍然没有拉出新信号

目标：既然 `pressure-order` 会把 `p32/r4` 平顶结构压成尖峰，那就单独给这类结构做 `plateau32` family，看能否只修 `param_p32_r4_n40` 而不伤主线。

1. `v227`：`plateau32` candidate family
   - 思路：从 `v221` 出发，只在 `r=4/p>=32`、`fg` 高于下界、且当前 best state 是“大平台”时启用
   - family 内不做 generic pressure-order，而是：
   - 只对触碰 plateau row 的 flow，用 `row_hist + per-job used + job-hash` 在近似等价端口里做去相关 tie-break
   - 结果：
   - `param_p32_r4_n40`: 保持 `69.28`，`MM 3.75`
   - `param_p32_hot`: 保持 `69.95`，`MM 3.75`
   - `medium_32 / medium_25 / proxy_3 / proxy_7 / proxy_8`: 全部回到 `v221`
   - `submit_core`: `957.97`（与 `v221` 完全持平）
   - 判断：这条 family 至少说明 **“平台去相关 tie-break”是安全的**，不会再像 `pressure-order` 那样把 `p32` 顶到 `4.00`
   - 但它也没有进一步把 `3.75 -> 3.50/3.25` 推下去，说明只改候选生成 tie-break 还不够强
2. `v228`：`plateau32_rebalance`
   - 思路：不从头造 candidate，而是从当前 best state 出发，只对 plateau hot row 做小规模 move，尝试把 `15` 平台往下推
   - 再接一轮 `global_swap + lns`，看能否把“平台宽度下降”转成真正的 `fg/MM` 改善
   - 结果：
   - 与 `v227` / `v221` 完全一致：
   - `param_p32_r4_n40`: `69.28`，`MM 3.75`
   - `submit_core`: `957.97`
   - 判断：**轻量级 plateau rebalance 也没有抓到真实可动空间**
3. `v229`：`plateau32_core_rebuild`
   - 思路：承认单 flow move 不够，把当前 job 里触碰 plateau row、且当前就压在热端口上的 flow 抽成一个 `64~128` 的 core
   - 先整批卸载，再按 `local_peak -> future_fg -> plateau hot hits -> core 内去相关 -> row_hist` 重排，最后接 `global_swap + lns`
   - 目标是：在不回溯历史 job 的前提下，用“当前 job 内协同重排”去逼近真正需要的 multi-job 去相关
   - 结果：
   - `submit_core`: `957.97`
   - `contrast`: `574.73`
   - `guardrail`: `411.43`
   - `param_p32_r4_n40 / param_p32_hot / medium_32 / medium_25`: 最终输出和 `v228` **完全一致**
   - 判断：
   - 这说明问题已经不是“当前 job 协同强度还差一点”，而是 **当前 sequential 在线框架下，这条 `p32/r4` plateau32 case 基本没有可转化的局部自由度**
   - 至少在当前算子族里，再继续加大 `plateau32` 的 core rebuild / rebalance 强度，预期也只是在同一个 basin 里空转
3. 这两版的含义：
   - 当前已经可以基本确认：`param_p32_r4_n40` 这类 `p32/r4` 平顶 case，不是简单靠
   - “generic pressure-order”
   - “端口 permutation”
   - “平台 gate”
   - “轻量 post-pass rebalance”
   - “当前 job 内协同 core rebuild”
   - 这几类从轻到中的修补都已经验证过了，还是推不动
   - 结合前面的 set-cover 结果（所有 hot cell 需要多个历史 job 共同覆盖），当前更合理的结论是：
   - **这条 `p32/r4` plateau32 case 在当前 sequential 框架里接近不可再压**
   - 后续主线不该再围绕它继续深挖，而应回到更可能转成线上收益的 proxy-like `r=4` 候选质量 / 接受准则问题

### 差距分析：2.64 分到第一名

**线上现状**：v199 = 369.36，第一名 = 372.00，差距 2.64 分（6 个 case）
