### param_extreme_r2 深度分析

唯一有 gap 的 case：当前 Maxsingler=1.50 (jm=3)，结构下界=2 (=r)。

**Job 结构分析：**
- 40 个 job 中，37 个可以用 CSP greedy（100次随机排序）达到 jm ≤ 2
- 3 个 hard job（job 1/31/39）：228 flows, m=11, 13-17 tight cells
- 这 3 个 job 决定了整体 Maxsingler

**搜索实验：**
- CSP greedy 1000次随机排序：最好 5 violations（job 1）
- Walksat 200k iterations from best greedy：降到 2 overloaded cells
- Multi-start walksat 20 restarts × 100k iterations（Python, 402秒）：降到 **1 overloaded cell**，无法到 0

**结论：** 这 3 个 hard job 虽然结构上可行，但搜索空间极度受限（r=2, p=32, 228 flows × 11 phases），本地搜索方法在合理时间内无法找到可行解。

### v131 冲突指标后处理探索（Cinphsc / Cbttskc）

**v131a — Cinphsc reduction（max_phase_load约束）**
- 思路：把流从 overflow port (load > r) 移到 underload port (load < r)，约束不增加 max_phase_load
- submit_core: 1015.20 → 1015.23 (+0.03)
- Cinphsc 几乎不变（proxy_5: 6788→6774, proxy_1: 397→385）
- **结论：约束太紧。bottleneck phase 中 ALL ports 都在 max 附近，无 headroom 可用。**

**v131b — Cinphsc reduction（global future_gmax约束，放松per-port）**
- 思路：放松约束为"不超过全局 Maxmultir"，允许 target port 的 max_phase_load 增长
- submit_core: 1015.20 → 1006.99 (-8.21) ❌
- proxy_1 Maxsingler 2.50→2.75, proxy_3 2.50→2.75, param_n40_hot 1.25→1.50
- **结论：放松约束导致 Maxsingler 退化，得不偿失。**

**v131c — Cbttskc reduction（降低 peak phase port 的 max_phase_load）**
- 思路：找 peak phase 上的流，移到有 headroom 的 port，降低源 port 的 max_phase_load → 降低累积 → 降低 Cbttskc
- submit_core: 1015.20 → 1014.75 (-0.45) ❌
- param_n40_hot Maxmultir 4.50→4.75（移动流改变了 max_phase_load 分布）
- medium_25 Cbttskc 9812→9678 (-134), medium_32 11006→10347 (-659) 有效果
- 但 Cbtphsc 增加 + Maxmultir 退化抵消了收益
- **结论：移动流会破坏 card-port consistency（增加 Cbtphsc）并可能恶化 Maxmultir。**

### 冲突后处理方向总结

| 方向 | 约束 | 结果 | 根因 |
|------|------|------|------|
| Cinphsc reduction (tight) | max_phase_load | +0.03 | overflow 是结构性的，total > p*r 时不可约 |
| Cinphsc reduction (relaxed) | future_gmax only | -8.21 | Maxsingler 退化 |
| Cbttskc reduction | max_phase_load + gmax | -0.45 | 破坏 Cbtphsc + Maxmultir 退化 |

**核心发现：** 冲突后处理的根本矛盾是——任何移动流的操作都同时影响 Cinphsc/Cbttskc/Cbtphsc/Maxmultir 四个指标。在当前已高度优化的状态下，改善一个指标几乎必然恶化另一个。Cbtphsc 方向（port_consistency/neutral_swap/relaxed_swap）之所以有效，是因为它们有"负载中性"或"严格不增加 max"的安全保证。而 Cinphsc/Cbttskc 方向没有类似的安全操作空间。

### v139-v142 score-aware PC 细调

**v139 — future_sq delta**
- 思路：把 `global pressure` 从线性近似改成更直接的 `future_sq` 峰值收益估计
- submit_core: 1085.02 → 1084.73 (-0.29)
- 固定对抗集: 307.16 → 307.05
- 现象：`medium_31`、`param_n40_hot` 都退化
- **结论：** 这会过度追逐 source/dst peak relief，反而破坏了 v138 当前较好的平衡。

**v140 — peak-aware pressure**
- 思路：只有 flow 真的碰到当前 peak phase 时，才计入 source relief
- submit_core: 1085.02 → 1085.04 (+0.02)
- 固定对抗集: 307.16 → 306.99
- **结论：** 比 v139 稳，但收益太小，而且固定对抗集退化，不足以进主线。

**v141 — strict-improve hybrid**
- 思路：只有 target port 能直接把该 source-card 的 `Cbtphsc` 压低时，才启用 score-aware；否则回退旧 `can_move`
- submit_core: 1085.02 → 1084.09 (-0.93)
- 固定对抗集: 307.16 → 306.96
- **结论：** 新口径下退化更明显，说明 `v138` 的收益不只来自“立刻降低 source-card Cbtphsc”的 move；等价 Cbt 场景下的搬移也可能有价值。

**v142 — gate on `base_cbt>=2`**
- 思路：只对冲突更重的 source-card 启用 score-aware，避免为单个 phase 边界去搬流
- submit_core: 1085.02 → 1084.34 (-0.68)
- 固定对抗集: 307.16 → 306.97
- **结论：** refresh 后不再只是“接近追平”，而是明显落后，说明 `base_cbt=1` 的 card 上确实存在真实收益，不能简单整段关掉。

**本轮结论：**
- `v138` 已经把“一维 tie-break / 简单门控”这条线吃得很干净。
- 下一步不该继续堆标量 pressure 指标，而应该转向 **two-port lookahead / phase-aware port_consistency / 小范围多目标分配** 这类更高阶的结构改动。

### v143-v151 per-port second-stage refine

在 `v138` 之后，主线没有再从标量 tie-break / 简单 gate 中拿到有效增量，于是开始尝试把 `port_consistency` 从“整张 source-card 统一并到一个 target port”改成“两阶段”：
1. 第一阶段仍保留 `v138` 的 score-aware group-level `port_consistency`
2. 第二阶段只在 source-card 内，对某个当前 port 的一部分 flow 做更细粒度的 `per-port refine`

#### v143 — useful-move group PC

- 改动：group-level `port_consistency` 的候选评估和执行都只统计真正会改变 source-card phase port-mask 的 move；执行时对选中的 target 反复搬到没有 useful move 为止
- submit_core: 1085.02 → 1085.05 (+0.03)
- 固定对抗集: 307.16 → 307.15
- **结论：** 结构方向是对的，但纯 group-level useful-move 版本增量太小，还不足以进主线

#### v144 — per-port refine 初版（失败）

- 改动：在 group-level PC 之后追加 `run_port_consistency_perport_refine`

- 结果：`proxy_1/2/3/4/5/6 + medium_25/32 + bench_15` 大面积 30s timeout，submit_core 只剩 607.33

#### 这一轮的结构结论

1. 第一优先级先排查 `v138` 的线下→线上转化率异常高：搞清楚到底是缺少哪类 proxy case、缺少哪种 `p/r/m/used_cnt` 结构，还是当前 manifest 分层对这类收益估计偏保守。

#### 这两次补试的结构结论

1. 单纯继续细调“什么时候允许继续交替”这一层 gate，已经很难从 `v163/v166` 上直接再拿到 `submit_core` 正增量。
2. `v167` 证明：给中等大 job 单独开后门，只会复现 `v166` 的换分，不会自动恢复 `medium_25/32` 的主集收益。
3. `v168` 证明：额外交替链的有效部分不是狭义的局部连锁，因此下一步不该继续压成 targeted chain。
4. 后续更值得尝试的点，应回到 **second-stage 候选质量本身**，而不是继续堆 gate：
   - 只对第一轮 `main PC` 真改过 port-mask 的 card 做更强候选评估，而不是只看“是否动过”
   - 在 second-stage 内加入更小范围的 `two-port lookahead`
   - 直接围绕 `proxy_11` vs `medium_25/32` 的 source-card 结构差异，找出“为何同样的交替链会一个修回、一个掉分”的特征
