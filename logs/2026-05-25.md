## 详细记录

### v250: SA 单邻相 prefport 提案

**思路：** 在 `v232` 的 SA 单流换端口里，优先尝试“邻相候选并集收缩成单一端口”的 prefport 提案，测试更强的局部 proposal bias 是否能继续放大 `submit_core` 上的 SA 收益。

**实现：**

- 仅当相邻 phase 已用端口并集收缩成单一端口时，优先把该端口作为 SA move 目标
- 未命中时回退到随机目标端口
- 线上提交并与 `v232` 做实分对照

**结果：**

| 数据集 | 旧（v232） | 新（v250） | Delta |
|--------|-----------:|-----------:|------:|
| submit_core | 959.03 | 959.14 | +0.11 |
| contrast | 575.64 | 575.67 | +0.03 |
| prefport_veto v2 | 388.54 | 388.40 | -0.14 |
| guardrail | 413.08 | 412.65 | -0.43 |
| online | 369.65 | 369.56 | -0.09 |

**结论：** `submit_core` 小涨但线上回落，说明 prefport proposal bias 这条线不能靠主集微增判安全。`v250` 也是当天补建 `prefport_veto v2` 的直接触发点。

### v251: SA 邻相 prefport vote

**实现：**

### reverse locate: 基于 `v232` 前线上版本统一反向定位

**思路：** 不再只盯 `v255` 一次失配，而是把 `v232` 之前已经拿到线上结果的主线版本统一放到当前口径下对比，反推哪些本地增量 historically 是可转化的，哪些只是反复出现的假提升。

**实现：**

- 重新编译并复评 `v138 / v163 / v199 / v214 / v230 / v232`
- 统一按当前 `submit_core + contrast` 口径做 per-case diff
- 对照真实线上增量，按 family 聚合：
  - `proxy_hot = proxy_3/5/6`
  - `medium_hot = medium_25/32`
  - `proxy_wide = proxy_7/9/10`
  - `lowr_contrast = medium_31 + param_r2_p32_hot + param_extreme_r2`
  - `p32 = param_p32_hot + param_p32_r4_n40`
  - `param_hot = param_r3_hot + param_n40_hot`
  - `contrast_proxy = proxy_11/12`
  - `contrast_medium = medium_29/30`

**结果：**

| 区间 | 本地增量 | 线上增量 | 主导本地增量 | 统一判断 |

### transfer_holdout v1: 历史近邻低转化诊断层校准

**思路：** `reverse locate` 只告诉我们“哪些 family 历史上低转化”，还需要确认新建的 `transfer_holdout` 作为 manifest 时，是否真能在 `v232` 邻域把这类假增益放大出来，同时不被误读成新的 `prefport_veto`。

- 按三簇读取：`lowr_contrast`、`medium_25/32 + p32`、`param_hot`

**结果：**

**结论：** `transfer_holdout` 是有效的，但它的作用不是“把坏分支排到更低”，而是**放大近邻分支里那些 historically 低转化的本地增量**。`v214` 和 `v255` 都符合这个特征；`v232` 也会在这层上涨，说明它不能替代 `submit_core` 或升级成新 veto。后续正确用法应是：当两个版本在 `submit_core` 上接近时，若额外领先主要集中在 `transfer_holdout`，且更宽的 proxy-like 层没有同步走强，就先判为低置信度，不直接提交。

- 每次线上出现“本地接近但实分分歧”的版本对，都按 family 写明主导增量来源，避免只留下最终线上分数
- 继续沿 `v214 -> v230 -> v232 -> v255` 这条链补中间态观察；当前历史提交已经足够判断“哪些 family 常低转化”，但还不足以把 `transfer_holdout` 直接压成单层硬排序规则

### manifest v3: backbone / anchor / holdout 重组

**思路：** 旧 `submit_core` 把 proxy backbone、mixed-transfer anchor、以及 near-neighbor low-transfer 信号混在一起，导致 `v232` 邻域版本很容易被局部 family 抬分。要解决这个问题，不能只继续补 `transfer_holdout`，而是要把三种角色拆开。

**实现：**

- 新增 `datasets/submit_backbone.txt`：`proxy_1..10 + bench_15`
- 新增 `datasets/submit_anchor.txt`：`medium_25/32 + param_p32_hot + param_p32_r4_n40`
- 将 `datasets/submit_core.txt` 收窄为兼容入口，当前等价于 `submit_backbone.txt`
- 将 `datasets/transfer_holdout.txt` 收窄为 `lowr_contrast + param_hot + lowr_*`
- 同步更新 `datasets/README.md`、`AGENTS.md`、`CLAUDE.md`、`algorithm-iterate/SKILL.md`

**结果：**

| 指标 | 旧 | 新 | 结论 |
|------|----|----|------|
| 主排序层 | `submit_core` 混合 backbone + anchor | `submit_core/backbone` | 收窄 |
| 次级佐证层 | 无 | `submit_anchor` | 拆出 |
| 低置信度诊断层 | `transfer_holdout` 混有 anchor family | `lowr + param_hot + lowr_*` | 收口 |
| 兼容性 | 旧命令依赖 `submit_core` | `submit_core == submit_backbone` | 保留 |

**结论：** `transfer_holdout` 不删，也不并入 `submit_anchor`。前者是 near-neighbor 低转化集中度告警，后者是次级正向佐证；如果合并，版本读法会更乱。当前正确顺序应是：先看 `submit_core/backbone`，再看 `submit_anchor` 是否 corroborate，最后用 `transfer_holdout` 判断增量是否只是 low-r / param-hot 集中。
